# T4 — Concurrent dispute updates

GET /api/disputes/{id} returns a strong ETag for the currently persisted revision. PUT to that URI requires a specific If-Match validator. Missing header returns 428; malformed header or wildcard returns 400; well-formed but stale or weak validator returns 412. Accept a valid comma-separated list if one strong tag matches. Missing resources are 404 before evaluating preconditions. On success, update exactly once atomically, advance the revision, and return the new representation and ETag. Same revision concurrent PUTs must yield one 200 and one 412. Tags must survive app restart and never repeat for the same existing resource. The persisted numeric revision is returned as revision in GET/PUT and list items; POST still creates a dispute. Existing databases without a revision column must open safely.

React sends the ETag the user originally edited, not a later background refetch tag. On 412 display a conflict alert, refresh list and detail, retain the unsaved note and status, and do not implicitly retry. The operator can explicitly rebase the draft using a button labelled “Use latest version” after refreshed data arrives, then press Save to retry against that revision. Show the latest server note independently of the draft. Mutation or refetch responses with lower revisions must not overwrite newer server state. Keep existing controls accessible and maintain normal save and document behavior.
